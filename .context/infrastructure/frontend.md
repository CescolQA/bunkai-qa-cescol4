**SECURITY CHECK**: no secret-looking name found under the `NEXT_PUBLIC_` prefix (no `NEXT_PUBLIC_*_SECRET`, `*_SERVICE_ROLE*`, `*_TOKEN`, etc.). `SUPABASE_SERVICE_ROLE_KEY` and `SUPABASE_JWT_SECRET` correctly stay unprefixed and server-only (`lib/env.ts`, `server-only` marker) — confirmed clean.

**Cross-reference to the `backend.md` naming mismatch**: the mismatch found there (`.env.example` declares `SUPABASE_PUBLISHABLE_KEY`/`SUPABASE_SECRET_KEY`, but `lib/env.ts` validates `NEXT_PUBLIC_SUPABASE_ANON_KEY`/`SUPABASE_SERVICE_ROLE_KEY`) **does affect one client var**: `NEXT_PUBLIC_SUPABASE_ANON_KEY` is the actual browser-exposed var the app boots against, but `.env.example` never declares that literal name — it declares `SUPABASE_PUBLISHABLE_KEY` instead (no `NEXT_PUBLIC_` prefix at all in the example file). A contributor following `.env.example` literally would set an unprefixed var that Next.js never inlines into the client bundle, on top of the app failing its own Zod boot check. Same root cause as `backend.md`, restated here because it is specifically a client/browser-bundle concern, not just a server-boot one.

## Routing + State + Auth integration points

> **This section is consumed by `/adapt-framework` to wire test fixtures — precision matters more than prose here.**

### Router

- **Next.js App Router**, confirmed: `app/` directory exists with route segments (`(app)`, `(auth)`, `about`, `api`, `auth`, `design-tokens`, `invites`, `qa`); **no `pages/` directory exists** (`ls pages/` → not found) — this is a pure App Router app, not a mid-migration hybrid.
- `typedRoutes: true` in `next.config.ts` — route strings passed to `<Link href>`/`router.push` are type-checked; a test helper building URLs programmatically should mirror the actual route param shapes (`[projectSlug]`, `[atcId]`, `[testId]`, `[runId]`, `[milestoneId]`, `[id]` for workspace members, `[provider]` for OAuth) rather than hand-building strings.
- Full route map (9 public / 16 protected / 8 dynamic) is already documented in `.context/PRD/user-journeys.md` §1 — reused here, not re-derived.
- Route-protection gate lives in `middleware.ts` (`PROTECTED_PREFIXES`), not in per-page client code — a test fixture that needs to assert "redirected to `/login?next=<path>`" should hit the middleware behavior directly rather than a page-level guard.

### State management

- **No client-side state management library** — repo-wide `dependencies`/`devDependencies` grep confirms no `zustand`, `redux`/`@reduxjs/toolkit`, `jotai`, `recoil`, `@tanstack/react-query`, or `swr`. The only `@tanstack/*` package is `@tanstack/react-table` (data-table rendering, not data fetching/caching).
- **Data fetching pattern**: Server Components read data directly via `lib/supabase/server.ts` (SSR, cookie-scoped, RLS-respecting); Client Components call `/api/v1/**` via native `fetch()` or invoke colocated Server Actions (e.g. `app/(app)/projects/[projectSlug]/atcs/[atcId]/actions.ts`) — no client-side cache/query layer sits in front of either path. This means: **no stale-cache invalidation quirks for tests to work around** (no React Query `queryClient.invalidateQueries` equivalent to wait on), but also **no built-in request deduplication/retry** for a test harness to lean on — each `fetch()` is a one-shot call.

### Auth client integration

- **Browser Supabase client**: `lib/supabase/client.ts` — `createBrowserClient<Database>()` from `@supabase/ssr`, module-level singleton (`cached` var) guarding against React strict-mode double-mount creating duplicate `GoTrueClient` instances. Reads `NEXT_PUBLIC_SUPABASE_URL`/`NEXT_PUBLIC_SUPABASE_ANON_KEY` via static `process.env.X` access (required for Next.js to inline them into the client bundle — explicit code comment warns never to import the server-only `lib/env.ts` from this file).
- **SSR client**: `lib/supabase/server.ts` (cookie-scoped, used by Server Components and Route Handlers — see `architecture.md` Component Structure table).
- **Session lifecycle**: `middleware.ts` refreshes the Supabase session cookie on every request and redirects unauthenticated users away from `PROTECTED_PREFIXES` to `/login?next=<path>`.
- **Two parallel auth methods, unified server-side**: cookie session (browser UI) and Bearer PAT `bk_pat_*` (headless/CLI/agent) both resolve to one `Principal` shape via `lib/api/principal.ts` `resolveIdentity()` (ADR-0001) — this is a backend concern already documented in `architecture.md`, restated here only because a UI-driven test fixture (Playwright) will always go through the **cookie** path (`createBrowserClient` + `middleware.ts`), never the PAT path; PAT is exclusively for API-level test fixtures.
- **Fixture implication for `/adapt-framework`**: a Playwright UI fixture should log in through the real `/login` flow (or seed a session cookie directly via the Supabase server SDK) rather than trying to invoke `createBrowserClient()` out of band — the singleton-cache pattern in `client.ts` assumes a live browser `window`/module context.

### Test IDs strategy

- **`data-testid` is the established, actively-used selector strategy** — confirmed present, not absent: **446 occurrences across 47 files in `components/`**, **176 occurrences across 36 files in `app/`** (622 combined in actual UI code; the repo-wide total of 895 includes non-UI doc/`.context` references, excluded from this count). No `data-cy` or other test-id convention found.
- **A written convention already exists in the target repo**: `.claude/skills/sprint-development/references/data-testid-standards.md` — documents a definition-vs-usage placement rule (generic UI primitives like `Button`/`Input`/`Card` get `data-testid` where *used*, not in their own definition; domain-specific components like a `ShoppingCart`-equivalent get it in their own definition) and a semantic-naming convention. This is the target repo's own testability doctrine, not something this QA repo needs to invent.
- **Conclusion for `/adapt-framework`**: `data-testid` is a **reliable, first-class selector strategy** for this project — Page Object / component locators should default to `[data-testid="..."]` over CSS classes or text matching, consistent with the target repo's own documented convention.
